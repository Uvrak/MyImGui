DOSBox-X / MyImGui – Stand 22.08.2026

HEUTIGER STAND

1. Memory Read Tracking

Der MemoryReadTracker kann inzwischen nicht nur gelesene Speicheradressen erfassen, sondern auch die DOSBox-Instruktion, die den jeweiligen Speicherzugriff ausgelöst hat.

Aktuelle API:

MemoryReadTracker::record(address)
MemoryReadTracker::record(address, instructionAddress)

Zusätzlich:

start()
stop()
clear()
active()
addresses()
instructions()
recordInstruction()
instructionTransitions()

Damit können wir inzwischen mehrere Ebenen untersuchen:

- Welche Speicheradresse wurde gelesen?
- Welche Instruktion hat diese Adresse gelesen?
- Welche Instruktionen wurden ausgeführt?
- Welche Übergänge zwischen Instruktionen fanden statt?


2. Instruction Tracking

Neu hinzugekommen ist das Erfassen der ausgeführten Instruktionen.

Im DOSBox-X CPU-Core wird die aktuelle Instruktionsadresse aufgezeichnet.

Dadurch können wir nicht mehr nur einzelne Speicherzugriffe betrachten, sondern auch den tatsächlichen Ablauf des Programmcodes verfolgen.

Besonders interessant ist:

instructionTransitions()

Damit können wir untersuchen:

Instruktion A -> Instruktion B

und dadurch nachvollziehen, wohin der Programmfluss nach einer bestimmten Instruktion weitergeht.


3. Disassembly-Fenster

Für die Disassembly wurde ein eigenes Fenster angelegt.

Das war notwendig, weil der normale Memory Viewer durch die zusätzlichen Funktionen zunehmend unübersichtlich wurde.

Das Disassembly-Fenster zeigt DOSBox-Speicher als x86-Code an.

Zydis wird dafür als Disassembler verwendet.

Das Fenster besitzt eine Adresseingabe und kann direkt zu einer bestimmten Adresse springen.


4. Navigation

Der Sprung zu einer Adresse funktioniert inzwischen.

Beispiel aus dem heutigen Test:

0x0F5A4

Von dort konnten wir den tatsächlichen Programmfluss weiterverfolgen.

Eine weitere beobachtete Adresse war:

0x0F631

Damit können wir jetzt wesentlich gezielter vom Memory-Tracking in die Disassembly wechseln.


5. Register

Bei der Analyse sind unter anderem folgende x86-Register relevant geworden:

AX
SI
DI

AX:
Allgemeines 16-Bit-Arbeitsregister.
Wird häufig für Berechnungen, Rückgabewerte und Speicheroperationen verwendet.

SI:
Source Index.
Wird häufig als Quelladresse bzw. Index für Speicherzugriffe verwendet.

DI:
Destination Index.
Wird häufig als Zieladresse bzw. Index für Speicherzugriffe verwendet.

Gerade SI und DI können bei MM3 interessant sein, wenn Datenstrukturen, Charakterdaten oder Tabellen durchlaufen werden.


6. Farbliches Hervorheben identischer Hexwerte

Eine wichtige UI-Idee vom heutigen Test:

Identische Hexwerte bzw. identische Bytefolgen sollen farblich hervorgehoben werden.

Dadurch könnten wiederkehrende Werte und Muster im Disassembly schneller erkannt werden.

Das soll insbesondere helfen bei:

- identischen Opcodes
- wiederkehrenden Speicherzugriffen
- gleichen Konstanten
- ähnlichen Instruktionsmustern
- Tabellenzugriffen


7. Aktueller technischer Stand

DOSBox-X kompiliert wieder erfolgreich.

Die vorher sichtbaren Meldungen wie:

conversion from const uint16_t to const uint8_t

waren Warnungen und verhinderten den Build nicht.

Der Fehler:

8. Wichtigste Erkenntnis

Wir bewegen uns inzwischen weg von einer reinen Suche nach RAM-Werten.

Der neue Ansatz ist:

RAM-Adresse
    ->
lesende Instruktion
    ->
Disassembly
    ->
vorherige/nächste Instruktion
    ->
Programmfluss

Damit können wir nicht nur herausfinden, WO beispielsweise ein MM3-Wert liegt, sondern zunehmend auch:

- welcher Code ihn benutzt
- wie der Wert verarbeitet wird
- welche Berechnung durchgeführt wird
- welche Bedingungen geprüft werden
- wohin der Code anschließend springt
