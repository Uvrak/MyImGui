============================================================
2. 0x2ACF4 MEMWR-UNTERSUCHUNG
============================================================

0x2ACF4 ist weiterhin nur eine SPUR.
NICHT als Cursoradresse betrachten.

Der neue Multi-MemWr-Logger zeigt, dass 0x2ACF4 ständig beschrieben wird.

Beobachtete Writer:

    0x16205
    0x16235

Beobachtete Written Values:

    0x00
    0x01
    0x02
    0x03
    0x04

Typisches wiederkehrendes Muster:

    0x16205 -> 04
    0x16235 -> 00
    0x16205 -> 01
    0x16235 -> 01
    0x16205 -> 02
    0x16235 -> 02
    0x16205 -> 03
    0x16235 -> 03
    0x16205 -> 04
    0x16235 -> 00
    ...

Cursor sichtbar -> unsichtbar erzeugte dort KEINE erkennbare besondere
Veränderung.

Schluss:
0x2ACF4 ist sehr wahrscheinlich kein einfacher Cursor-Boolwert.
Der Wert sieht eher nach Zähler/Index/State-Cycle aus.

4. GEMEINSAMES TARGET
============================================================

TrackingWindow besitzt weiterhin das gemeinsame:

Dieses Target soll langfristig gemeinsam verwendet werden für:

- Trace
- Trans
- Exec
- MemWr
- Memory Scanner
- Memory Viewer
- Disassembly
- weitere Memory Tools

Target wird über die bestehende Session gespeichert.

Problem gefunden:
Beim Programmstart wurde das geladene Target durch die automatische
Trace-Auswahl wieder überschrieben.

Entfernt wurde deshalb das automatische:

    snprintf(
        m_targetText,
        ...
        m_trace[m_selectedTraceIndex].address
    );

Zusätzlich:

    ~TrackingWindow()
    {
        saveSession();
    }

Damit wird die Session beim sauberen Programmende gespeichert und beim
Start wieder geladen.

8. AKTUELLER SCHLUSS
============================================================

Der Unterschied aus 0x2ACF4 ist real, aber bisher NICHT als
Cursorentscheidung bestätigt.

Die untersuchte Routine sieht eher danach aus, Daten bzw. einen Buffer

Das ist der nächste starke Kandidat für eine tatsächliche
zustandsabhängige Entscheidung.
